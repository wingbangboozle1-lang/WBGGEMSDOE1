2 · Why GEMSDOE32 B2 scored 0.2778 (user-reported) and whether a unique file can beat it

  1. What the file is. B2 is 37,654 dots and is a verified subset of B1 (40,199 dots; the same positives as GEMSDOE28 solo D2.8 and GEMSDOE31 solo D28) and of D2.8 (44,090 dots; GEMSDOE25 and GEMSDOE30). It is reached by removing dots that lie close to the mapped catalogue. 5.8% of its dots lie within 300 m of the mapped catalogue (29 Oct audit, user-reported file).
  2. Mechanism (interpretation, not tested). The shared metric (vendor/gems57/metric.py) is DTI = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w), with a 3 px (300 m) triangular kernel. A dot near a mapped fault but far from any hidden fault is counted as a false positive under that kernel. Removing such dots raises DTI when the removed dots carry little true credit. This is a precision-by-exclusion explanation; no run here tested it.
  3. Evidence and its limit. Descriptively, across the nine sites in the 29 Oct audit, a higher near-catalogue share goes with a lower reported score (Spearman −0.93, p ≈ 0.0002, n = 9). The scores are user-reported and unverified, and the files come from a small number of families.
  4. Why our proxy cannot settle it. The holdout's truth is the withheld catalogue segments (20% per quadrant fold), so that truth is itself catalogue-shaped. Closeness to the visible catalogue alone reaches AUC 0.887 on that truth (leakage rule: 0.90). Files that sit near the catalogue therefore score high on the proxy, and B2 scores lowest. Rank agreement between the user-reported scores and the holdout is Spearman -0.862 (p = 0.0006, n = 11). The proxy therefore reverses the reported ordering.
  5. Can a unique file beat 0.2778? Not demonstrated. Any file made by pruning B2 is a subset of B2, so it would sit near 100% within 3 px of B2 and fail the lane rule. The only test that can produce a number is one organizer-scored submission. That needs a DrivenData login, which this sandbox does not have.

5 · Irregularities flagged for review

  • Leaderboard figures in the brief do not match the live page. The brief says 0.4413 is the top and 0.3195 is the highest score. On the live page (fetched 31 Oct 2026), #1 is 0.4544, #2 is 0.3925, and #46 is 0.3261. 0.3195 is not in the top 46 on the 31 Oct page. Leaderboard.
  • The literal 70% gate. AGENTS.md lists it as degenerate for lattice-type rasters. This session also found 11 of 482 registry rasters over 70% for the candidate, including the r13 lattice (99.995%) and GEMSDOE25 gem1 magnetics (0.7711). The owner should decide which measure governs.
  • Portal format convention is unresolved. The official sample uses NaN outside the footprint (7,111,787 cells, per the 29 Oct note). The shared writer and validator use all-finite zeros outside, which is also within [0, 1]. Neither has been tested on the portal. The reported "[0, 1]" error cannot be reproduced locally.
  • Holdout ranks the reported files in reverse (Spearman -0.862). The proxy truth is catalogue-adjacent by construction. Do not use it to rank new candidates.
  • Shared-tool defect, worked around. The shared writer vendor/gems57/submission_writer.py creates outputs with mode 0600, which can block download. The file is hash-pinned upstream, so it was left unchanged; scripts/build_candidate_20261031.py sets 0644 after the write (the bytes are unchanged).
  • The bridge manifest names two scripts that do not exist (scripts/make_data_bridge.py, scripts/assemble_data_bridge.py). The restore worked through the pinned template instead.
  • The sample file in the bridge has 60,988 positives that match the catalogue exactly (from the 29 Oct note). It is a grid template, not a zero-fault sample.
  • The DrivenData leaderboard cannot be fetched by curl here (TLS error); the page was read with the fetch tool.

7 · Next steps and blockers (ranked)

  1. Owner decision on the gate. Choose whether the lane rule (70% of dots within 3 px) or the density-matched lift governs. The new file fails the first (77.1%). On the second, its median lift is 1.32 (1.0 = random).
  2. One organizer-scored test. Only a DrivenData receipt makes a score ORGANIZER-CONFIRMED. The owner has to upload from the portal. The file is not cleared, so do this only if the owner accepts the lane duplicate.
  3. Fold-safe candidate generation. Re-derive the catalogue exclusion per fold so that the holdout reading for the new file is valid.
  4. Resolve the NaN-versus-zeros convention against the official sample before any upload.
  5. Restore the four external catalogues listed as missing in data/external/ (free, official sources only), then re-run the leakage canary with them.
