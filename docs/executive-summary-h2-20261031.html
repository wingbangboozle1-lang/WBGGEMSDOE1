3. Why GEMSDOE32 B2 (0.2778, owner-reported) scored highest, and whether we can beat it

  1. Verified facts (audit JSON): B2 has 37,654 dots, 0 on the mapped catalogue, 0 within 1 px or 2 px of it, and 2,171 (5.8%) within 3 px. Its nearest rival D2.8 is a 44,090-dot file. The 2026-10-29 analysis states that B2 is a pruned subset of D2.8, removing 6,436 dots that lay within 2 px of catalogue traces. Source: docs/data/nine_site_audit_20261029.json, docs/unique-lane-summary-20261029.html. We did not re-derive the subset claim this session.
  2. Mechanism (first-order, algebra): with DTI = TP/(TP + 0.2·FP + 0.8·FN), let D be the current score and c a dot's expected kernel cover of truth. Removing that dot raises the score only if c > 0.2·D/(1 − 0.8·D). At D = 0.2778 the threshold is c > 0.0714. Dots with less than about 7% expected cover are net-negative to keep. Pruning dots that sit next to known faults is a plausible way to remove such dots, but this is a derivation, not a measurement.
  3. Competing evidence (our holdout, our experiment E2): on the holdout, random dots with no catalogue avoidance score 0.0478, 3-px avoidance 0.0374, 6-px avoidance 0.0204. The holdout therefore rewards proximity to visible faults. The holdout hides catalogue segments, which are continuous with visible traces. The competition's hidden labels are new faults, which are not in the catalogue. The holdout cannot test the pruning mechanism behind B2. This is the central validity problem (see §5).
  4. Can we beat 0.2778? Not demonstrated. The best unique candidate has no paired holdout gain (§2). The only real signal is the owner-reported leaderboard values, and a leaderboard check needs an organizer receipt. A calibration ladder on the portal is the fastest way to learn. Each upload uses a weekly slot (three per week under rules §3.4), and this is a user action.

4. The literal uniqueness rule cannot be satisfied by a dot file

The project's literal lane rule says a file fails if more than 70% of its dots lie within 3 px of one registry raster's dots. A uniformly random dot field of the same size fails it too, so the rule is a control-tested blocker for every dot file:

  • Random dot field, trial 0: 3 literal duplicates, worst overlap 99.87% vs 20261001_r13-lattice-s5_v2_nan-outside
  • Random dot field, trial 1: 3 literal duplicates, worst overlap 99.87% vs 20261001_r13-lattice-s5_v2_nan-outside

Decision needed (owner): replace the literal rule with a density-matched rule, or accept that no dot file can ever be cleared. We have not changed the rule. Changing it is an owner decision.

5. Holdout validity: the central irregularity

On the random arm, catalogue avoidance lowers the holdout score: 0.0478 with none, 0.0374 at 3 px, 0.0204 at 6 px. That direction is the opposite of the leaderboard evidence (§3). The holdout is therefore not a valid proxy for the catalogue-avoidance lever. Recommendation: stop using the holdout to choose dot placement, and calibrate with organizer receipts instead.

6. Portal error "Predicted values must be in range [0, 1]"

  • Official text (problem page): float32 values between 0 and 1, and "data outside the bounds is null or nan."
  • Conflict: the shared validator (vendor/gems57/validate.py) requires zeros outside the footprint and no NaN anywhere. The official text and the official sample (sample_submission.tif, NaN outside, per registry note) say NaN. The repository's own writer comment (src/gems/submission.py) says some portal validators reject NaN outside, but this is unverified.
  • The candidate uses all-finite zeros outside, the convention of the previously scored files named "zeros", so the candidate follows the repo's convention. This choice is a risk to flag, not a verified fact.
  • We cannot see the user's failed upload, so the actual cause is unverified. Likely causes: NaN inside the footprint, values outside [0,1], or NaN outside the footprint.
