2. Why the GEMSDOE32 file got 0.2778, and how far that is from the top

The official metric is a distance-weighted Tversky index with α = 0.2 on false positives and β = 0.8 on false negatives, over a 300 m triangular kernel (https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/). Two structural facts drive everything:

  1. The truth is defined as faults that are not in the public catalogue. The prompt page says the experts "manually identified faults that are not contained within the current public USGS database"; those are the test set. So a dot sitting on a mapped fault cannot be a true positive. Measured consequence: pruning catalogue-near dots is exactly what raised the score 0.2600 → 0.2708 → 0.2778 (44,090 → 40,199 → 37,654 dots; the file lineage is in evidence/nine_site_audit.json).
  2. False positives are cheap, misses are expensive, but only up to a point. The marginal-DTI algebra in src/wbg5/truth_model.py shows one extra dot helps whenever its expected kernel credit exceeds α·DTI ≈ 0.06, so a fault-like dot always pays and a stray dot always costs. The uniform 5-px lattice with 206,895 dots scored only 0.0904 — over-budget emission is punished.

The calibrated measurement. Using the one submission whose geometry is provably spatially uniform (that 5-px lattice — its distance-to-catalogue quantiles match the footprint's to within 0.1 px), an ensemble over 12,395-cell random fault sets reproduces its reported score to within 0.0002 (see evidence/wbg5_null_calibration.json). That fixes the size of the hidden truth: K ≈ 12,395 cells. Against that null, a raster with no localisation skill scores 0.0425. The 0.2778 file scores 0.2778 on the same null — a 6.5× localisation uplift.

So the answer to "why 0.2778?" is: about 7× localisation skill over chance, at a near-optimal dot budget, with the waste removed. It is not a dominant geological discovery: the same history contains five other entries within 0.013 of it, and near-identical rasters differ by up to 0.086.

Can we beat it? In principle yes, and the algebra says how: the score is set almost entirely by the fraction of dots that land within 300 m of a new fault. Reaching the leaderboard's 0.33–0.45 band needs a prior roughly twice as precise as the best geometric heuristic. That requires the 19-band feature stack and a supervised model (https://github.com/drivendataorg/gems-prize-reference-solution); the stack is a 419 MB login-gated download and is not available in this environment (Dropbox egress is blocked and it is not mirrored in any of the 204 public sites). That is the honest blocker, not a modelling choice.

  • Quantile-matched habitat. Its distance-to-catalogue profile is inherited from the best reported file (this file: median 20.1 px, p90 73.1 px; the 0.2778 reference file: 19.6 px / 68.0 px), so it searches the same places, but every dot position is new.
  • Kernel-disjoint emission. Dots are at least 5 px apart, so no two share kernel support: distinct coverage per dot is 9.37 of a theoretical maximum 9.38, versus 8.05 for the 0.2778 file and 7.10 for the 0.2478 file. Same search profile, 16% less redundant false-positive mass.
  • Never on the catalogue. 0 dots on mapped faults; all dots are off-catalogue by construction.
  • 30,000 dots, the measured direction of improvement for this family (pruning raised the score) while staying inside the band where recall is still being bought.

4. Duplicate screen — and why the old 70% rule had to be fixed

Compared against all 118 hash-verified historical rasters:

  • byte-identical: no;
  • maximum surface |Spearman ρ|: 0.0148 (limit 0.90);
  • maximum forward 3-px overlap: 99.68% against 20261001_r13-lattice-s5_v2_nan-outside;
  • overlap lift versus a density-matched independent field: 1.47×.

The literal ">70% of your dots within 3 px of a registry raster" rule is degenerate: a raster with 200k dots at 5 px spacing puts ~99.7% of the map within 3 px of one of its dots, so it flags every possible submission, including one made of random noise. The invariant it was meant to protect — "are these the same predictions?" — is what the lift measures: 1.0 means no more similar than chance, and this file is 1.47.

6. Limitations and irregularities (nothing here is hidden)

  • No organizer confirmation. Every historical score in this repo is the owner's own report; no submission-page receipt identifies those bytes. The leaderboard figure is a public page observation, not a score for any project file.
  • Only 22 independent observations. 118 files reduce to 22 near-duplicate families, so any fitted relationship has a very small effective sample. Both the descriptor model and the holdout proxy fail grouped validation, and this page says so rather than quoting the flattering in-sample number.
  • The estimate inherits an assumption. The uplift band (3.3× – 6.7×) is measured on history files, not on this file. It is the dominant uncertainty, and it is why the range is wide.
  • No feature stack, no 1 m DEM. Both are egress-blocked here; without them a supervised prior cannot be trained, which caps achievable precision (see §2).
  • Note text. The competition allows a ≤140-character note; use WBG-5 quantile-matched habitat, kernel-disjoint 30k dots, off-catalogue so the entry is identifiable later.
