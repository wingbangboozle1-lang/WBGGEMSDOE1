Reason: the project's literal parallel-run gate (STOP if more than 70% of a submission's dots lie within 3 px of one registry raster's dots) is measured at 99.68% against the r13 lattice. A random set of 30,000 dots drawn inside the footprint scores 99.86% on the same test, so the gate rejects any dotted file while r13 is in the registry. That makes it a rule decision, not a WBG-6 property.

Decision needed from the owner (one choice)

  1. Exclude r13 from the registry (it is a synthetic calibration lattice from this repo, not a competitor submission) and keep the literal 70% gate for real submissions. WBG-6 then needs a full check against all scored rasters (not yet run here; measured against the nine named sites only).
  2. Keep r13 and drop the 3-px gate, accepting that no dotted file can pass it. Uniqueness then rests on the other checks (byte, surface correlation, nearest-dot profile).
  3. Adopt a density-matched rule (the repo's current substitute). This is a self-authored exemption that the repo's own AGENTS rules forbid, so it needs your explicit approval.

Why the 0.2778 file scored highest: what the bytes show

  • Nested pruning, verified by pixel test. All 37,654 dots of the 0.2778 file are also in the 44,090-dot file (GEMSDOE25/30, 0.2600). The 40,199-dot file (GEMSDOE28/31, 0.2708) is also a strict superset of 0.2778. The 0.2778 file is the 44,090-dot file with 6,436 dots removed.
  • What was removed. Dots within 3 px of the mapped catalogue fall from 19.5% (44,090-dot file) to 5.8% (0.2778 file). No file has a dot exactly on the catalogue, so the catalogue proximity itself is what changed.
  • Mechanism (proposed, not proven). The hidden truth is new faults that experts labelled, so a dot on or beside a mapped fault is more likely to be a false positive. With alpha=0.2 and beta=0.8, removing dots with little credit can raise the Tversky index. The metric is official (docs.nlr.gov 96647 §3.2; competition page 967).
  • Monotone pattern across the ten rows. Spearman between user-reported score and catalogue-adjacent share is ρ = −0.997 (n = 10, about 7 distinct dot sets, so the p-value is not a valid test). This is a descriptive ordering, not a validated predictor.
  • Confounders not separated. Dot count, catalogue share and site/family are strongly tangled. The 60k-dot files score lowest and have the highest catalogue share. With n = 10, the relation cannot be attributed to one cause.

Three candidate hypotheses (untested, ranked by testability, not by expected score)

  1. H1 — Catalogue-adjacency suppression at matched count. Layer: mapped-fault catalogue only (already in data/bridge). Signature: share of dots within 3 px of catalogue below 6%, at a fixed dot count. Not in the catalogue: it targets un-mapped structure only. Mimic: a dense lattice away from faults that scores well for other reasons. Status: needs a holdout that ranks submissions; the repo's own holdout does not (Spearman 0.144, n=118).
  2. H2 — Count-matched nested pruning. Take a dense family (44,090 dots) and remove dots by catalogue proximity to reach a chosen count. Test: compare with random removal at the same count. Status: the 0.2778 file is one such prune; a matched-random control has not been run.
  3. H3 — Dot-count confound. Test whether the ordering survives equal-count controls (for example, random subsets of the 44,090-dot file at 37,654 dots). Status: cannot be run without the 19-band feature stack (not in the repo; Dropbox egress blocked).
