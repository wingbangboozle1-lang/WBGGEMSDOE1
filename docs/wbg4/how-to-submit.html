Why "Predicted values must be in range [0, 1]" happens — and how WBG-4 prevents it

  • Root cause: If a portal validator runs an unmasked array check such as ((arr >= 0.0) & (arr <= 1.0)).all(), any NaN pixel (even outside the study footprint, where IEEE-754 NaN >= 0.0 evaluates to False), any ±Inf, or any float overshoot (-1e-7 or 1.000001) triggers "Predicted values must be in range [0, 1]".
  • Automated WBG-4 guarantee: scripts/run_wbg4_lane.py routes predictions through the shared submission_writer.py in zeros mode and verifies the written GeoTIFF on disk via scripts/validate_submission.py across all 12,279,160 pixels (3730 × 3292): single-band float32, EPSG:32611, nodata=None, n_nan = 0, n_inf = 0, min = 0.0, max = 1.0, 0 outside-footprint positives, and 0 mapped-catalogue positives.
  • Official text vs local safety policy: The official problem description states that cells outside the bounds should be null/NaN, whereas empirical Focus-site evidence (GEMSDOE32 B2 -zeros.tif) and strict whole-array range checks favor finite 0.0 outside the footprint. Local format validation is a preflight check, never a guarantee of organizer portal acceptance.
