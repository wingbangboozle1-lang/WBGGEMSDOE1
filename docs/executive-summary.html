Why the reported 0.2778 may be high — and what it does not prove

Metric mechanics (official): predictions are confidence values in [0,1]. Ground-truth and predictions receive distance-weighted matching credit using a triangular 300 m support (three 100 m pixels). The competition uses DTI α=0.2 for false positives and β=0.8 for false negatives. Consequently, nearby predictions can still receive partial credit, while omitted true-fault pixels are relatively costly. The complete official equations are linked below.

Empirical clue (OWNER-REPORTED; no submission receipt independently checked): the GEMSDOE32 owner-maintained report describes a related H19-5 sequence: 0.1922 (OWNER-REPORTED) for the dense form, 0.2600 (USER-REPORTED) after D2.8 thinning, 0.2708 (USER-REPORTED) for the B=1 form, and 0.2778 (USER/OWNER-REPORTED) for the B=2 form. The progressively smaller supports and rising reported score are consistent with pruning low-value pixels/false-positive burden while retaining candidate locations close to held-out faults. But without the exact scored bytes, an organizer receipt, and access to private labels, this is an association—not a proven causal explanation. It does not establish that the removed pixels were false faults or that the remaining predictions are new geological discoveries.

Scientific interpretation: the high score is plausibly a favorable operating point on a sparse-prediction/recall trade-off under a distance-tolerant metric, possibly combined with good spatial correspondence to the particular public test faults. It could also reflect candidate selection, leakage, accidental overlap, or unreported variants. The public record alone cannot discriminate these explanations. The appropriate test is a fold-local, segment-buffered hide-and-recover evaluation that exactly emulates the metric, paired against the existing holdout best—not a score inferred from the leaderboard.

Can it beat 0.2778? Maybe; not demonstrated here. A higher score on one public test set is not proof of better discovery, and this checkout has not run a holdout. The correct answer today is “unknown; no submission authorized.”

Exactly how to submit — only after the project says “OK TO SUBMIT”

  1. Wait for this project to show green `OK TO SUBMIT` and provide a named candidate TIF. A file marked research-only or negative is not eligible.
  2. Download the offered single-band GeoTIFF (or a ZIP containing exactly one GeoTIFF). Verify the displayed SHA-256 against the run card.
  3. On DrivenData, open the GEMS competition's New submission form and select the TIF in “File to submit”. The project must already have validated the saved file: one band; float32; CRS EPSG:32611; same dimensions, bounds and transform as `sample_submission.tif`; values finite and in [0,1] inside the footprint; outside footprint null/NaN.
  4. Enter the generated short unique name and the run-card comment (maximum 140 characters) in “Note”. Names/comments are identifiers, not a substitute for raster uniqueness.
  5. Submit only if a slot is available under the portal's current cap. Save the submission receipt; only that receipt can establish `ORGANIZER-CONFIRMED` score evidence.
Why the earlier range error happens: the competition requires predictions in [0,1]. A raw model logit, z-score, or standardized feature may be negative or greater than one. Any future inference must apply a documented probability/confidence mapping, clip only as a deliberate post-processing choice (not to conceal errors), and reopen the written GeoTIFF to test range across valid cells before any download is enabled.
